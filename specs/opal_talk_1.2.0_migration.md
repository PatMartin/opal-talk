# OPAL Talk — migration to contract 1.2.0 (OPAL Suite Standard v1.2)

**Status: ACTIVATED.** `opal_talk.1.2.0.yaml` is now the live contract (root + packaged copies
updated in the same commit). `opal_talk.1.0.0.yaml` is retained for reference only.

This is a **breaking** contract revision relative to v1.0.0: the error envelope changed to
`OpalError`, mutating operations on logical configuration gained mandatory `If-Match`
preconditions, and four operations were added (`patch_talk_settings`, `get_talk_health_live`,
`get_talk_health_ready`, `validate_talk_backup_payload`). All deltas below are implemented.

## Contract deltas (1.0.0 → 1.2.0)

### Changed operations

No operations are removed. The per-key settings routes are **retained** for OPAL suite
consistency, but gain the standard concurrency and error behaviour:

| operationId | Route | Change |
|---|---|---|
| `get_setting_api_v1_settings__key__get` | `GET /api/v1/settings/{key}` | Returns `ETag`; echoes correlation headers |
| `upsert_setting_api_v1_settings__key__put` | `PUT /api/v1/settings/{key}` | Requires `If-Match` (428 missing, 412 stale) |
| `delete_setting_api_v1_settings__key__delete` | `DELETE /api/v1/settings/{key}` | Requires `If-Match` (428 missing, 412 stale) |

### New operations

| operationId | Route | Shape |
|---|---|---|
| `patch_talk_settings` | `PATCH /api/v1/settings/` | Atomic whole-settings patch. Body: object, `minProperties: 1`. Requires `If-Match`. 200 returns the updated settings object. |
| `get_talk_health_live` | `GET /api/v1/health/live` | `OpalHealthProbe` `{status: ok\|degraded\|unavailable, ready: bool, details?}`; 200 or 503. |
| `get_talk_health_ready` | `GET /api/v1/health/ready` | Same schema; 503 when the service cannot serve traffic. |
| `validate_talk_backup_payload` | `POST /api/v1/backup/validate` | Validate a supplied backup/export **payload** (JSON body, not files) without side effects. Existing `GET` variant stays. |

### Behaviour changes

1. **Correlation headers on every route** — request params `X-Opal-Session-Id`,
   `X-Opal-Transaction-Id`, `X-Opal-Request-Id`, `X-Opal-Causation-Id` (all optional,
   opaque printable ASCII 1–128, pattern `^[!-~]+$`; invalid client values → 422).
   Every response — JSON, error, streamed, binary — echoes them. Missing transaction/
   request IDs are generated by the service. Session ID is context-only, never auth.
   (See the normative text in the contract's `info.description` and
   `x-opal-context-standard`.)
2. **Strong ETags + mandatory `If-Match`** — `GET` on engines, voices, profiles,
   settings returns an `ETag` (a strong revision of the logical configuration).
   Mutations `PATCH /engines/{id}`, `PATCH /voices/{id}`, `DELETE /voices/{id}`,
   `PATCH /profiles/{id}`, `DELETE /profiles/{id}`, `PATCH /settings/`,
   `PUT /settings/{key}` and `DELETE /settings/{key}` require
   `If-Match`: missing → **428**, stale → **412**.
3. **`201 Location`** — `POST /voices/` and `POST /profiles/` return `Location`.
4. **New error envelope** — all service errors (including 412/428/422) use
   `OpalError`: `{"error": {code, message, request_id, transaction_id, session_id?,
   causation_id?, details?}}`. This replaces both the current `{code, message, details}`
   body **and** the FastAPI `{"detail": [...]}` validation shape — request validation
   failures must be remapped (add a `RequestValidationError` handler).
5. **Pagination/concurrency metadata** — `x-opal-context-standard` records the suite
   conventions (config lists are full arrays, no pagination needed today; cursor rules
   apply only to future history endpoints). No-op for current resources, but keep the
   conventions in mind for new endpoints.
6. **Streaming** — context headers must be present in the streamed response headers;
   failures after headers are sent stay "abrupt termination" (unchanged semantics).

## Implementation plan (suggested order)

1. **Correlation middleware** (`api/` or `service/`): parse + validate the four
   headers (422 on malformed), generate `transaction_id`/`request_id` when absent,
   stash on `request.state`, and stamp all four headers on every response — including
   `StreamingResponse` and exception-handler responses (do it in a middleware that
   wraps the whole app so error paths are covered). Add the four names to
   `OPAL_HEADERS` in `app.py` for CORS `expose_headers`.
2. **Config revision + ETag/If-Match**: a single `config_revision` row in the store,
   incremented inside every `transaction()` that mutates engines/voices/profiles/
   settings (backup restore/import count too). `ETag: "r<n>"` on the listed GETs; an
   `If-Match` FastAPI dependency (`Header(...)`) on the eight mutating routes raising
   428/412. Keep it global-revision-simple — the contract asks for a revision of the
   logical configuration, not per-resource versions.
3. **Error envelope**: replace `error_body` with the `OpalError` shape populated from
   `request.state` IDs; override FastAPI's `RequestValidationError` handler to emit
   `{"error": {code: "unprocessable_entity", details: {"errors": [...]}, ...}}`.
   `InvalidRequest` folds into the same shape. Check the CLI/SPA error describers —
   they parse `code`/`detail` and must learn the new envelope.
4. **Settings PATCH**: `SettingsService.patch(dict)` — validate known keys, apply
   atomically in one transaction, return the full map. The three `{key}` routes stay;
   `PUT`/`DELETE` gain the standard `If-Match` precondition, so CLI `settings set KEY
   VALUE`/`settings delete KEY` and the SPA SettingsPanel must fetch the settings
   `ETag` (`GET /settings/` or `GET /settings/{key}`), send `If-Match`, and retry
   once on 412.
5. **Health probes**: `/health/live` → `ready: true, status: ok` always (process is
   up); `/health/ready` → 200 `ready: true` when at least one enabled engine is
   available, else 503 `status: unavailable, ready: false` — reuse
   `Services.health()` logic.
6. **POST `/backup/validate`**: feed the request body through the existing
   `ConfigService.validate_candidate` path (`ConfigExport.model_validate` first),
   return the `ValidationResult`-shaped report. No store writes.
7. **`Location` headers** on voice/profile creation: `/api/v1/voices/{id}` /
   `/api/v1/profiles/{id}`.
8. **Swap the contract**: root `opal_talk.yaml` ← 1.2.0 content, repackage
   `src/opal_talk/contract/opal_talk.yaml`, bump `__version__`/`pyproject` to 1.2.0,
   update `OPERATIONS` (`cli/client.py`), `COMMANDS` (`cli/main.py`),
   `spa/src/api/operations.json`. The parity tests enumerate whatever is missed.
9. **Tests**: extend `tests/contract.py` — it already validates response headers
   against the spec, so correlation headers and ETags get checked automatically once
   declared. Add explicit tests for: malformed correlation header → 422, `If-Match`
   missing → 428 / stale → 412, settings PATCH atomicity, 503 on `health/ready`
   when no usable engine, `Location` on creates, backup-payload validation.
   SPA: `contract.test.ts` + workflows will need the new operations wired into
   `client.ts` panels.
10. **Docs**: update `USER_GUIDE.md` (§5 conventions: ETag/If-Match replaces "last
    write wins"; error envelope; settings PATCH; probes), `CLI.md`, and add
    1.2.0-specific notes to `CONTRACT_NOTES.md` (e.g. where `details.errors` carries
    the old `loc` list).

## Compatibility notes

- `GET/PUT/DELETE /settings/{key}` are retained, so `opal talk settings get/set/delete`
  keep their UX — but `PUT`/`DELETE` now require `If-Match`: clients fetch the current
  `ETag`, send it, and retry once on 412.
- The `InvalidRequest` 422 `detail` list moves under `error.details`; keep the
  `loc`/`msg`/`type`/`input` items so existing tooling still parses.
- `If-Match` on `DELETE` is required even for deleting non-existent resources
  ("DELETE without existence is still subject to the precondition").
